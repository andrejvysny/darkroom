# Native application API

`core-model::catalog` owns the existing camelCase catalog query and read DTOs. `core-library` re-exports their previous paths and retains all SQL, filtering, sorting, paired-image and pagination semantics. `image_by_id` deliberately includes missing records, unlike the present-only library query. The process version and catalog schema are unchanged.

`core-app::ApplicationSession` owns immutable application snapshots and typed commands/completions. It contains no database, filesystem, GUI or GPU dependency. Library, selected-photo/editor identity, active first-slice effects and renderer capability have separate read models. Jobs expose immutable records and admission metrics in the application snapshot. Edit transactions/history, durable writes and preferences remain separate feature services.

Construct a session with injected `Clock`, `EventSink` and renderer-capability ports. `dispatch(Command)` validates enabled state and payload, then returns immutable effects. Execute effects outside the state owner; return each typed `Completion` through `complete`. Never execute an obsolete effect: `is_current` verifies its token and payload. Catalog lifecycle effects must execute in order. Cancellation cannot reverse physical IO. `AsyncCatalogWorkflow` preserves physical lifecycle ordering and final publication fences.

Catalog open/close/reopen/shutdown advance `CatalogEpoch`. Every selection, including the same image and A–B–A, advances editor session and selection generation. Query and metadata requests have independent checked, monotonically increasing IDs. Replaced requests cannot publish old completions; wrong outcome kinds and wrong image IDs are rejected. Accepted query changes clear old rows/count, so failed reads cannot relabel an old result as the new filter. Snapshots remain immutable through shared ownership.

`subscribe` immediately supplies the current snapshot. Each subscription holds one latest `SnapshotUpdate` with a typed notice, revision, timestamp and complete snapshot. Updates coalesce; revision gaps are observable and the snapshot is the recovery source. This is a state-change feed, not a lossless job-terminal event queue. `close` or dropping the subscription tears it down; dead entries are pruned. Event sinks run after subscriber locks are released.

`core-runtime::CatalogAdapter` implements the narrow catalog port with the existing engines. It captures a connection generation, performs SQL with the shared connection lock, releases it, and validates the generation before returning owned values. File open and retired-connection destruction happen outside the slot lock. Replacement/close invalidates in-progress reads and opens. Errors retain actionable categories and original engine error chains. The explicitly named legacy connection bridge is for the Tauri composition root; widget code receives no database or general service locator.

`AsyncCatalogWorkflow` composes paths, clock, event sink, renderer-capability port and effect executor for the native host. The application session stays on the event thread; one catalog effect executes at a time on the supervised executor. At most eight current pending effects are retained, with obsolete queries/selections coalesced. Open/close are durable lifecycle effects and execute in physical order. `pump` never waits for IO; completion wakes the host through a coalesced callback. The host waits for the final close and joins workers before exit. `wait_idle` is the blocking headless adapter. The synchronous `CatalogWorkflow` remains available for compatibility tests.

The five temporary legacy commands `library_query`, `library_count`, `library_folders`, `library_date_tree` and `image_meta` call the same catalog adapter. Startup uses the shared open/error classification and preserves the host's fatal dialog wording. Unmigrated commands share the same connection through the compatibility bridge. Their assigned feature owners remain recorded in `tests/migration/parity`; this does not claim those commands are migrated.

The native host accepts `--catalog PATH` to display real catalog records, select metadata, page, refresh, close and reopen the supplied catalog. `--catalog-probe PATH` exercises open/query/selection/shutdown without a GUI. Neither route discovers a production catalog implicitly. The default no-argument foundation probe and `--gpu-probe` remain available. Catalog open follows existing migrations; qualify using a copy of an existing catalog.

`core-runtime::jobs::Supervisor` owns a fixed worker pool and typed `JobHandle<T>` results. Every job has an ID, catalog/editor owner, class, immutable captured inputs, progress, admission reservation and cancellation state. Ordered lanes serialize per owner and class; latest requests replace pending work and request cancellation of matching running work; deduplication returns the existing job ID. Rejected latest intents also invalidate matching running results, but return explicit backpressure to the caller. Admission never silently drops an accepted durable command. One worker is reserved for foreground commands/viewport work during normal operation; remaining workers choose foreground, visible thumbnails, bulk work, then prefetch.

Count and estimated-byte budgets cover queued, running and retained result payloads until consumption or handle drop. Latest queued replacement reclaims its reservation atomically. Terminal records are bounded; a retained handle can still query its own terminal status after central-history eviction. Progress coalesces independently from the single-consumer terminal result. `CancelRequested` records an intent, not completed cancellation. Running disposable results are discarded at completion; durable successful work reports success even if cancellation was requested after it began. Task/wake panics and worker start/join failures are observable. Task and payload destruction runs outside executor locks.

`ManagedWorkers` owns the small bounded set of long-lived host adapters. Shutdown stops producer admission and the filesystem watcher, sets phase cancellation flags, stops thumbnail/prefetch producers, drains accepted durable executor work, drains sidecar intent, then joins adapters. Phase initialization cannot clear cancellation after shutdown starts. In-flight decode, GPU submission and model training have cooperative boundaries; they are not forcibly interrupted. A shutdown wait is not evidence that unsaved edits became durable; that policy belongs to the persistence service.

The temporary Tauri adapter routes blocking commands through this shared executor. Its default host configuration is three workers, 64 admitted jobs, a 2 GiB estimated reservation budget and 256 central records. Reservations are scheduling estimates, not a hard bound on engine allocations or total process RSS. Per-photo analysis, watcher indexing and feature backfill decode sequentially; numerical engines retain their existing bounded internal parallelism. Infrastructure workers wait for admission outside executor workers, so a full queue cannot deadlock an import waiting to enqueue its follow-up.

Thumbnail/sidecar pending sets are capped at 4096 IDs. Overflow requests a paged catalog rescan rather than losing durable intent; thumbnail pages contain 256 IDs. Prefetch retains at most eight IDs and a five-entry, 384 MiB CPU LRU, rejecting oversized entries. Watcher events occupy one coalesced slot and path traversal streams. Feature backfill retains one coalesced trigger and reads pages of 16 records. Catalog identity/status maps and query result sizes remain proportional to catalog input; reservation metrics do not claim otherwise.

`PublicationGate` fences final sidecar, thumbnail, preview-cache, feature and analysis publication against delete/relink/reset, including replacement that reuses an image ID. Capture source path/hash plus the mutation sequence before unlocked computation; revalidate the token at final publication. Writers acquire the publication gate before the DB mutex. Filesystem operations execute after releasing the DB mutex; source identity mutation waits for final publication. The gate is a short-lived publication barrier, not a document ownership lock. Generic runtime tests use staged files and SQLite rows to exercise paused publication races.

The legacy viewport adapter uses supervisor-assigned host IDs, rather than client counters that restart when a webview reloads. It claims the current image and ticket under the publication barrier before rendering; a delayed older worker cannot replace a newer owner. The React viewport scheduler owns its rAF, pointer/wheel listeners and lifetime generation. Owner replacement/unmount retires pending work, and Stage/Loupe reject late paints. Develop loads selected metadata independently when the Library page has not finished publishing its current rows, so rapid view navigation does not leave rendering permanently gated on missing dimensions.

Suggestion fitting and paged scoring run outside the shared catalog mutex. Candidate model promotion and all computed scores publish in one fenced SQL transaction; interruption before publication preserves the old model/scores. The host rejects scoring beyond one million input rows with an explicit error. Existing synchronous engine wrappers and scoring semantics remain available for compatibility.

The temporary compatibility host still calls legacy culling/deduplication Trash services with a borrowed SQLite connection, including thumbnail garbage collection. Those paths retain the shared catalog mutex across filesystem work. The executor and publication fence do not remove that lock boundary: those services still need a snapshot/work/publish split before the global no-catalog-lock-across-filesystem acceptance criterion can pass. Persistence acknowledgement and durable sidecar outbox policy remain separate from executor shutdown.

Validation:

- `cargo test -p core-app -p core-model -p xtask`
- `cargo test -p core-runtime -p core-library`
- `cargo test -p darkroom --lib`
- `cargo clippy -p darkroom -p darkroom-native -p core-runtime -p core-app --all-targets -- -D warnings`
- `cargo xtask layers` and `cargo xtask parity`
- With the explicit isolated baseline host and test bridge running: `DARKROOM_NATIVE_CATALOG=1 npx playwright test tests/native/catalog-wiring.spec.ts --project=tauri` from `e2e/`.

The runtime/catalog tests use copied temporary catalogs and deterministic channel-controlled replacement races. Native platform builds still require the codec environment documented in `docs/native-platform-builds.md`. The catalog UI is the first application slice; it does not yet provide photo presentation, editing, import or export.
